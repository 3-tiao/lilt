# 文档维护：编写与审阅

目标是让读者知道 lilt **是什么、能做什么、怎么用**，并能沿文档入口找到可信的细节。文档不是实现的证明；测试绿色、链接有效也不能证明文字正确。

## 两种职责

| 模式 | 角色 | 产出与边界 |
|---|---|---|
| `write` | 文档工程师 | 接收实现者的行为变化与证据，同步相关文档；或按明确的文档任务改写；可以编辑文档 |
| `review changed [base]` / `review full` | 文档测试工程师 | **只读**核对主张与证据、读者路径、链接和表达；报告发现，不直接修改代码或文档 |

默认：实现或产品行为变化时，实施者交代变化与验收证据，由 `write` 负责文档；完成编写后执行 `review changed`。用户要求周期审阅时用 `review full`；也可指定页面、专题或基线。审阅发现交回 `write` 修改，再复核受影响部分。两个角色可以依次执行，但**同一上下文里的自查不称为独立审阅**；真正独立复核须由未参与编写的审阅者另行执行，只有用户明确要求委托时才启动子 agent。

与其他内部 skill 的分界：`architecture-audit` 判断工程设计是否必要，只读、不负责文档修复；`usability-test` 通过实际运行检查人能否完成任务，不用文档充当体验证据。本 skill 只管文档的事实、覆盖、结构与可读性；发现实现或产品意图冲突时记录矛盾，不凭文案偏好改代码。

## 共同的证据顺序

1. 确认分支、commit、工作树状态、范围与面向的读者；未提交改动属于本次审阅对象时须说明。
2. 从 [`docs/README.md`](../../../docs/README.md) 定位权威文档；对外命令/参数/模型/错误以 `lilt api --json` 和 `docs/client-api/` 为准，持久化、播放与 UI 以各自规范及相应实现为证据。涉及外部服务、竞品或时效性事实，查原始来源并注明核实时间；无法核实就标明未知，不臆测。
3. 把每条重要主张落到实际行为、代码/测试或外部契约，尤其核对：可用平台/来源、功能已实现还是计划中、成功与失败路径、安装与命令示例、前置条件、限制与链接。测试可能只是复述文档，不算独立证明。
4. 区分“文档过时”“实现违背已定契约”“设计/产品意图未定”。前两类提出应改哪一方及理由；第三类提出待决问题，不能简单以当前代码为准覆盖设计。链接脚本只验本地链接/锚点，不验事实。

## 单一来源（DRY）

会变化的事实只在一个**权威位置**定义，其他地方只留摘要 + 指向权威的链接；发现同一清单/矩阵在多处复制时，先收敛再改。

- 权威位置的选择：对外命令/参数/模型/错误 → `docs/client-api/`；**支持哪些来源（服务）** 与**平台 × 引擎矩阵** → [`docs/product/roadmap.md`](../../../docs/product/roadmap.md) 的“支持的来源（服务）”与“平台与引擎”；实现/Phase 状态 → [`docs/internals/providers/providers.md`](../../../docs/internals/providers/providers.md)；持久化 schema → `docs/internals/persistence/`；UI 行为 → `docs/ui/`。
- 典型易漂移清单：支持的服务/来源、平台与引擎矩阵、命令与参数表、错误码、当前进度、快捷键。它们只能在权威处展开，别处链接。
- 使用者入口（`README*.md`）可以保留简短摘要以回答“是什么、怎么用”，但必须链接权威且不得声称“完整/唯一”。
- 改动顺序：先改权威位置，再修引用与摘要；`review` 把重复清单本身列为发现（即使各处当前内容一致）。
- 不为省字而牺牲可读性：链接要能独立读懂其上下文，不能让读者为了一个名词跳三次。

## `write`：随变更维护

- 从实施者交接的**用户可见结果和契约**推导文档影响面，而不只根据改过的文件名搜索：先改唯一权威规范，再改受影响的使用指南/README 摘要，必要时更新索引、skill 与路径引用；没影响就说明为什么无需改文档。
- 面向使用者写任务、前置条件、结果、限制；技术细节只用于回答“这是什么、能做什么、怎么用”，深入设计留在 `docs/`。README 不复制 API 表、错误码、实现状态流水账。
- 用可运行的示例并逐项核对 flags、输出及平台差异；仅在有依据时写“已实现”“支持”“始终”“唯一”。过时内容直接删或修正，不留兼容副本；不要为文档维护新增台账或模板。
- 以删减、合并或链接取代重复扩写；保持中文、标题层次、术语与邻近文档一致。若存在矛盾且意图不清，保留证据并问用户，不把推断写成事实。
- 完成后查旧路径/旧说法残留，把修改范围、行为依据和待核实项交给文档测试工程师；提交前遵守 `AGENTS.md` 的 `just verify` 门禁。不自动提交、推送。

## `review`：独立核验

- `changed`：用指定基线到当前工作树的 diff 定范围，包含已暂存、未暂存及新增未跟踪文件；从实现改动反向寻找应该变化的文档，从文档改动正向验证其主张及相邻入口。不要只检查 diff 中出现的 Markdown。
- `full`：按使用者路径（根 README → 安装 → 首次播放 → 常用指南 → 已知限制）与开发者路径（文档地图 → Client API → internals → testing/product）抽样关键主张；覆盖各平台/来源与近期高变动区域。记录实际检查范围，不能以抽样声称全仓无误。
- 分别检查：**事实**（与代码/契约/时效性来源是否一致）、**可操作**（命令、前置条件、失败说明）、**可读**（访客能否找到下一步、技术术语是否必要）、**体量**（同一事实是否多处复制、细节是否放错层）。不要凭行数或个人风格偏好制造问题。
- 输出按影响排序的问题清单：`文档路径:行号`、原主张、对照证据 `路径:行号` 或外部来源、对读者的影响、修正文档还是需要设计决策；区分已证实和未核实。最后列检查过的范围、未覆盖范围和建议的最小改动。若没有发现，不凑数。
- 审阅时运行 `python3 scripts/check-doc-links.py`（覆盖 `docs/` 与根目录 `README*.md`），并检查范围内非 Markdown 引用及旧路径残留；它只是证据之一，不替代事实与可读性审阅。默认只读，不主动启动真实播放；若脚本失败，报告具体链接，交回 `write` 修复。
