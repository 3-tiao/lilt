# 已发生的真实会话排障

先读仓库根目录 `docs/testing/integration.md` 的「已发生的真实会话排障」与「预发布使用与测试隔离」。该文档是流程和授权边界的权威来源；不要在本 skill 另存一套命令或协议。

## 何时使用

用户刚在日常 `just run` 或手动会话中遇到异常，希望查原因、读日志或对比播放与界面。只调查**已经发生**的事；主动组织陌生 agent 走查用 `usability-test`，Jira 工单/日志包用全局 `triage-analyze`。

## 排查顺序

1. **保留现场**：确定用户操作、时间窗、会话类型与运行构建。只读检查当前 socket、固定构建标识和现有日志；不要假定退出 TUI 就停了 server。手动会话可查 manifest/journal；日常会话不一定有这些文件。
2. **沿实际链路对照**：用户听到/系统面板看到的内容（只能向用户确认）→ helper 的当前歌曲与状态 → server response/watch → TUI 显示。先找首次分歧，再查相关代码与规范；进度在走、RPC 成功或假播放测试通过，都不能证明正在播放的歌名正确。
3. **区分证据与推断**：记录观察到的事实、构建/时间对应关系、可能原因及缺失证据。仅在有依据时确定根因；需要复现时先给最小、可验证的动作，不自己播放、跳歌或替用户结束会话。
4. **交付下一步**：用简洁中文说清“现象 → 首次分歧 → 可能原因/未知 → 下一项可验证动作”，附关键路径或日志位置；关系复杂才画小图或时间线。日志中的账号、令牌和媒体 URL 必须脱敏。

## 不得越界

- 默认只读：不启动 `just manual-test`（它可能替换旧手动会话）、不自动停止/重启日常 server、切引擎、清理日志、修改队列或进行有声复测。即使用户退出 `just run`，也须检查 server 是否仍在运行；部署前如需结束播放或暂停会话，明确说明影响并取得许可。
- 用户明确要求修复后，**另起实施步骤**：先写行为卡，补 hermetic 回归测试、同步文档并跑门禁；区分“测试通过”和“新构建真实播放已验证”。有声验证仍需用户明确授权和独占窗口，不用 fake 测试代替。
